# study-log 글 작성·발행 스킬

study-log(Gatsby + Notion 블로그, https://dhbang.co.kr)의 글을 **일관된 양식**으로 쓰고 발행하기 위한 절차. 이 파일은 오케스트레이션만 담고, 세부는 아래 두 문서를 **반드시 먼저 읽어** 따른다.

- `study-log/.claude/writing-style.md` — 문체·구조 원칙 (필수)
- `study-log/.claude/CLAUDE.md` — Notion 스키마, 발행 워크플로, Slug 규칙

---

## 1. 원고·소스 확보

- 사용자가 원고/PDF/링크를 준다 → 그 내용을 **재구성**한다(번역·복붙 금지, 저작권 유의: 직접 인용 최소화).
- 소스가 없으면 주제만 받아 초안을 쓴다.
- 시리즈 편이면 앞 편들과의 연결(Series, 이전 개념 재호출)을 확인한다.

## 2. 구조 — 일반 글

writing-style.md의 구조를 따른다. 뼈대:

```
> 출처/시리즈 attribution (한 줄)
## 도입        — 독자가 겪는 구체적 장면·현상 (의문형은 "~한 적이 있으신가요")
## 개념/메커니즘 — 항상 "왜?"에 답, 코드·구조는 인용(요약 금지)
## 한계        — 어디서 비싸지는가 / 언제 쓰지 말아야 하는가 (필수)
## 정리        — 표(2열+) + 한 줄 결론
## 참고        — 출처·링크
```

**소제목은 라벨이 아니라 주장문으로 쓴다.** 목차만 뽑아 읽어도 논지가 이어져야 한다.
(`정리`·`참고`처럼 기능이 고정된 섹션은 예외)

```
✗ 핵심 개념 — 흐름을 지배하는 결정 지점
✓ 라우터는 판단을 한 곳에 모아 나머지를 단순하게 만든다
```

**직접 겪은 사례 섹션은 넣지 않는다** (2026-07 결정). 정리형 글은 원문 해부에 집중하고, 개인 경험은 trouble/ 삽질기로 분리한다.
(예외: 아래 3-1 의 **따라 하는 실습기**는 직접 겪은 것이 본문이다.)

- 대섹션은 `---`로 구분, 표·인용구·코드펜스(언어 명시) 적극 사용.
- 경어체 `합니다/입니다`. 현상→원인 구조("버그처럼 보이지만 설계 의도다").

## 3. 시리즈(연재) 템플릿

연재 글은 위 구조 대신 **4단계 스파인**을 쓴다(각 편 일관성 유지):

```
> [저자·책/출처] · 시리즈 주제 (attribution 한 줄)
## 도입
## 핵심 개념 (무엇을·왜)
## 메커니즘·구조 (어떻게)
## 한계 (어디서 비싸지는가)
## (정리 + 한 줄 결론)
## 참고
```

각 단계의 소제목도 주장문으로 쓴다. 스파인은 순서를 정하는 것이지 제목 문구가 아니다.

- **Series 필드**를 시리즈명으로 설정 → `/series/<이름>` 페이지 + 편 간 prev/next 자동 생성.
- **Slug 중첩**: `study/<시리즈-슬러그>/<토픽>` (예: `study/agentic-design-patterns/prompt-chaining`).
  - 시리즈 랜딩/서문은 `study/<시리즈-슬러그>/intro`.
  - 파일과 하위 폴더는 이름이 달라 공존 OK, URL도 별개 → 충돌 없음.

### 3-1. 따라 하는 실습기 (2026-10, AWS EKS 실습기부터)

독자가 **처음 해 보는 사람**이고 글을 보며 그대로 따라 한다. 정리형 글과 다른 점만 적는다.

- 머리말 한 줄에 **이 편의 비용**을 적는다. 예: `> **AWS 프리티어 $200으로 EKS 실습하기 ③** · 💰 이 편도 돈이 나가지 않습니다. 비용 **$0**`
- 명령은 **실행 순서대로**, 각 명령 뒤에 **기대 출력이나 확인 방법**을 붙인다. "눈으로 확인" 단계를 만들지 않는다.
- 내가 실제로 밟은 실패(에러 원문)는 본문에 넣는다. 다만 독자가 따라 할 경로는 **성공한 경로 하나**다.
- 글에 싣는 코드를 원본에서 줄였다면 최소한 `validate`·`plan` 을 돌리고, **어디까지 확인했는지를 글에 적는다.**
- 🔴 **금액·시간·비율은 쓸 때마다 출처 행을 연다.** ①편에서 세 번 틀렸다(스냅샷 총액 `$2.94`,
  다른 구성의 `$170`·`60%`). 전부 "어딘가에 맞게 적혀 있는데 인용할 때 틀린" 경우였다.
- 편 사이의 약속("○편에서 다룹니다")은 발행 전에 실제로 지킬 수 있는지 확인한다.
- AWS 계정 ID·이메일·시크릿은 쓰지 않는다. 예시는 `123456789012`, `<본인 이메일>`.

### 3-2. 호흡과 그림 — 쓰고 나서 반드시 잰다

`writing-style.md` 의 「흐름 프로파일」과 「움직이는 그림」 절이 기준이다. 요지만 적는다.

- **문단으로 쓴다.** 생각 하나를 서너 문장에 걸쳐 풀고, 접속어(`그래서`·`하지만`·`예를 들어`)를 지우지 않는다.
  짧은 단정문을 일부러 심지 않는다. 🔴·⚠️ 는 편당 3개 이하, 문장 전체를 굵게 감싸지 않는다.
- 초안은 Notion 에 올리기 **전에** 잰다. 전부 ✅ 가 아니면 올리지 않는다.
  ```bash
  python3 .claude/skills/write-study-post/check-prose.py --flow <초안.md>
  grep -c "—" <초안.md>      # 캡션 라벨(Fig.1 —) 말고는 0 이어야 한다
  ```
- **그림**은 편마다 이해를 돕는 자리에 1~2장. 관계·흐름은 코드 블록 안 ASCII,
  상태가 바뀌는 것(켜고 끄기, 선이 올라가기)은 **움직이는 SVG**(`scripts/figures/<시리즈>/anim*.py`).
  mermaid 는 쓰지 않는다. 그림 안 문구는 질문형이 아니라 **결론을 말한다.**
  이미지는 `static/images/<시리즈>/` 에 커밋하고 본문은 절대 URL 로 건다(Notion 업로드는 만료된다).
- AI 가 그린 그림은 캡션이나 글 끝 인용구에 **AI 가 그렸다고 적는다.**

## 4. Notion 등록

`notion-create-pages`, parent = Study Log data source (`cfc0dc32-0c20-4846-aefe-3ced8939b68d`).

```json
{
  "Title": "...", "Emoji": "🧩",
  "Slug": "study/...", "Series": "시리즈명(단독글이면 생략)",
  "배포상태": "작성중",
  "date:Date:start": "YYYY-MM-DD", "date:Date:is_datetime": 0,
  "date:Last Updated:start": "YYYY-MM-DD", "date:Last Updated:is_datetime": 0
}
```

- **Tags** 허용값: Spring/JPA/Querydsl/Transaction/AI/Claude Code/Troubleshooting/AWS/EKS.
  예전에는 create 에서 multi_select 가 실패해 생성 직후 `notion-update-page` 로 따로 넣었다.
  2026-10-06 에는 `"Tags": ["AWS", "EKS"]` **배열**로 create 에 넣어 성공했다. 실패하면 예전 방식으로 돌아간다.
- 🔴 **한글을 `\u` 이스케이프로 손수 인코딩하지 않는다.** 그렇게 넣다가 `안팎`→`안팩`, `쌌`→`쌀` 로
  깨진 채 올라간 적이 있다. 평문 그대로 넣고, 올린 뒤 한 번 fetch 해서 읽어 본다.
- 본문의 `$` 는 그대로 쓴다. 변환기(`convert-notion.mjs`)가 수식으로 먹히지 않게 escape 한다.
- 본문에는 제목을 넣지 않는다(제목은 properties). attribution 인용구부터 시작.
- 시리즈 편은 date를 앞 편보다 뒤로 (prev/next가 date ASC 정렬).

## 5. 검토 게이트 (필수 — push 전 정지)

Notion 작성 완료 후 **반드시 멈추고** 사용자에게 보여준다:

- Notion 페이지 URL
- 제목 / Slug / Tags / Series
- 배포 예정 URL: `https://dhbang.co.kr/posts/{slug}/`

**사용자가 명시적으로 승인하기 전까지 배포하지 않는다.**

## 6. 배포 (승인 후)

1. Notion `배포상태` → `작성완료` (CI가 이 상태만 가져감), Last Updated 갱신.
2. CI 를 돌린다. **본문만 바뀐 경우 커밋이 필요 없다**(원본이 Notion 이라 레포에는 바꿀 것이 없다).
   ```bash
   gh workflow run ci.yml -R bangddong/study-log --ref main
   ```
   이미지·설정처럼 **레포 파일**이 바뀌었으면 브랜치 → PR → 머지로 올린다(머지가 CI 를 돌린다).
   예전 방식인 빈 커밋 push(`git commit --allow-empty` 후 `git push origin main`)도 여전히 동작한다.
3. CI 완료 확인: `gh run watch <id>` → success. CI가 마크다운 생성 + Notion을 `배포완료`로 자동 처리.
4. **라이브를 직접 확인한다.** 200 인지, 수식으로 깨진 곳이 없는지(`class="katex"` 0개), 낡은 숫자가 남지 않았는지.
5. 🔴 **이미 발행한 글을 고칠 때**: 변환기는 `작성완료` 만 가져간다. `배포완료` 인 채로 Notion 만 고치면
   CI 를 돌려도 **반영되지 않는다.** 상태를 `작성완료` 로 되돌린 뒤 2번을 한다.

## 발행 전 체크리스트

- [ ] 도입에 공감할 구체적 장면이 있는가
- [ ] 소제목만 뽑아 읽었을 때 논지가 이어지는가 (라벨 아닌 주장문)
- [ ] 모든 "왜?"에 답했는가
- [ ] 핵심 개념 정의에서 독자의 오해를 먼저 부쉈는가 ("A가 아니라 B다")
- [ ] 한 문단 안에서 `~입니다.`가 4번 이상 연달아 오는 곳이 없는가
- [ ] `check-prose.py --flow` 가 전부 ✅ 인가 (문단당 문장 3 이상 · 접속어 5~18% · 짧은 문장 12% 이하)
- [ ] 본문에 줄표(—)가 없는가
- [ ] 금액·시간·비율을 출처에서 다시 확인했는가, 글 안의 표와 서로 맞는가
- [ ] 그림의 숫자가 본문 표와 같은가, AI 가 그렸다고 적었는가
- [ ] 한계·비용 섹션이 있는가
- [ ] 직접 겪은 사례 섹션을 넣지 않았는가 (정리형 글만. 실습기는 예외)
- [ ] 코드/구조를 인용했는가(요약만 아님)
- [ ] 정리 표 + 한 줄 결론이 있는가 (단, 서문/랜딩성 글은 생략 가능)
- [ ] Slug에 카테고리 경로 포함, 시리즈면 중첩 규칙 준수
- [ ] Tags 가 들어갔는가
- [ ] 검토 게이트에서 사용자 승인을 받았는가
