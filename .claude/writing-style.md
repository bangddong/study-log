# Study Log 글쓰기 스타일 가이드

이 가이드는 Study Log의 모든 글에 적용되는 작성 원칙이다.
Harness Engineering 시리즈 글에서 추출한 패턴을 기반으로 한다.

---

## 글 구조

```
[도입]
독자가 직접 겪었을 법한 구체적인 장면이나 현상을 제시한다.
"이런 적 있지 않으세요?" 형태가 아닌, 독자에게 직접 묻거나 사실처럼 서술한다.
의문형은 "~한 적이 있으신가요?" 형태 (합쇼체 의문형 "~습니까" 금지).
예: "AI에게 같은 것을 반복해서 설명한 적이 있으신가요?"
예: "매 세션마다 같은 개념을 AI에게 다시 설명하고 있다면, 그건 컨텍스트가 쌓이지 않기 때문입니다."

[개념/메커니즘 해부]
- "왜?"를 항상 설명한다. 동작 방식만 나열하지 않는다.
- 이론/패턴이면 다이어그램 또는 구조 인용
- 코드가 있으면 반드시 인용. 요약만으로 끝내지 않는다.
- 소제목은 라벨이 아니라 주장문으로 쓴다 (아래 "소제목 = 주장문" 참고).

[한계]
그 개념/패턴이 어디서 비싸지는지, 언제 쓰지 말아야 하는지 한 섹션을 반드시 둔다.
비용을 다루지 않은 정리형 글은 홍보문으로 읽힌다.
제목 예: "어디서 비싸지는가", "이 패턴이 감추는 비용"

[정리]
- 표로 핵심 내용 요약 (2열 이상)
- 한 줄 결론: 이 글에서 독자가 가져가야 할 것 하나

[참고]
- 출처 명시 (링크 포함)
```

## 문체 원칙

### 소제목 = 주장문
소제목은 다룰 대상을 가리키는 라벨이 아니라, 그 절에서 하려는 주장을 담은 완결된 서술문으로 쓴다.
**목차만 뽑아 읽었을 때 글의 논지가 순서대로 이어져야 한다.**

> 나쁜 예: "핵심 개념 — 흐름을 지배하는 결정 지점"
> 좋은 예: "라우터는 판단을 한 곳에 모아 나머지를 단순하게 만든다"

> 나쁜 예: "메커니즘 — 라우터를 만드는 4가지 방법"
> 좋은 예: "라우팅 방식은 판단의 주체를 누구에게 맡기느냐로 갈린다"

주장문이 제목 자리에 오므로 제목 아래에 핵심 인사이트를 한 줄 더 쓰지 않는다(중복).
단, `정리`·`참고`처럼 기능이 고정된 섹션은 라벨 그대로 둔다.

### 현상 → 원인 구조
버그처럼 보이는 것도 설계 의도임을 밝히는 방식으로 쓴다.

> 나쁜 예: "/effort max를 설정하면 다음 세션에 사라집니다."
> 좋은 예: "/effort max를 설정했는데 다음 세션에는 사라져 있습니다. 이것은 버그가 아닙니다. `toPersistableEffort()`가 외부 사용자에게 max를 저장하지 않도록 설계된 결과입니다."

### "A가 아니라 B다" 정의문
개념을 정의할 때는 독자가 이미 갖고 있을 오해를 먼저 부수고 정의를 넣는다.
위 `현상 → 원인`의 일반형이며, 개념 정리형 글에서 주력으로 쓴다.

> "모듈화는 코드를 많이 나누는 일이 아닙니다. 같은 이유로 바뀌는 코드를 묶고, 다른 이유로 바뀌는 코드를 나누는 일입니다."
> "단순함은 복잡성이 없는 상태가 아닙니다. 복잡성이 이름 붙은 경계 안에서 다뤄지는 상태에 가깝습니다."

부정만 하고 끝내지 않는다. 반드시 대체할 정의를 붙인다.

### 독자 설정
"구현을 이해하려는 개발자." 개념을 처음 접하는 사람이 아닌, 이미 쓰고 있지만 왜 그런지 궁금한 사람을 대상으로 한다.

### 용어 처리
기술 용어는 한국어로 먼저 설명한 뒤 원어를 병기한다.
예: "컨텍스트 엔지니어링(Context Engineering)"

### 경어체
`합니다/입니다` 경어체. 구어체 섞지 않는다.

### 줄표(—)를 본문에 쓰지 않는다
한국어에서 `—`는 원래 거의 쓰지 않는 부호다. 영어 문체를 그대로 옮긴 흔적이라 밀도가 높으면 AI가 쓴 티가 난다.
**줄표가 하던 일의 대부분은 마침표가 더 잘한다.** 끊기 싫어서 대시를 쓰지만, 대개는 끊는 편이 낫다.

| 자리 | 대안 |
|------|------|
| 불릿 뒤 `**용어** — 설명` | `**용어입니다.** 설명` — 굵게 + 마침표로 같은 구조가 산다 |
| 문장 중 삽입구 | 마침표로 끊거나 쉼표·괄호 |
| 문장 끝 덧붙임 | 마침표로 끊어 새 문장 |
| 강조 라벨 `**순차 접근 — 5단계**` | `**순차 접근 (5단계)**` |
| 표 안 | 마침표 또는 쉼표 |

**이중 삽입(`— … —`)은 절대 쓰지 않는다.** 조사가 줄표 뒤에 붙어 한국어 문법이 깨진다.

> 나쁜 예: "처음의 질문 — 순서를 지킬 이유가 있을까 — 에 대한 답은"
> 좋은 예: "처음의 질문으로 돌아가 봅니다. 순서를 지킬 이유가 있을까? 답은"

**예외** — 아래는 남겨도 된다.
- 코드 블록 안의 주석
- 이미지 캡션의 `Fig.1 — ...` 라벨
- 참고문헌·외부 문서의 원제목

## 섹션별 작성 팁

### 도입 작성법
- 2~4문단
- 첫 문단: 독자가 겪는 상황 묘사
- 둘째 문단: 이 글에서 다룰 것 예고 (but 결론은 숨김)
- 독자를 설득해 다음 섹션을 읽게 만들어야 함

### 개념 해부 작성법
- 각 소제목은 "X는 Y다" 형태로 명확하게
- 구조/다이어그램 먼저, 설명 나중
- 구현 인용 시: 코드 블록 → 한줄 설명 → 왜 이렇게 설계했는가

### 직접 겪은 사례 — 넣지 않는다 (2026-07 결정)
- 초기 Harness Engineering 시리즈에는 "직접 겪은 사례" 섹션이 있었으나, Agentic Design Patterns 시리즈부터 **넣지 않기로 결정**했다.
- 책/자료 정리 글은 원문 내용 해부에 집중한다. 개인 프로젝트 경험은 별도의 삽질기(trouble/)나 회고 글로 분리한다.
- 삽질기·트러블슈팅 글은 경험 자체가 본문이므로 이 규칙과 무관하다.

### 정리 작성법
- 표: 개념/메커니즘 | 역할 | 핵심 설계 3열 구조 권장
- 마지막 한 줄: 이 글 전체를 관통하는 원칙 하나

## 선택 장치 — 글이 감당할 때만 쓴다

아래 둘은 체크리스트 항목이 아니다. **소재가 뒷받침할 때만** 쓴다.
억지로 넣으면 장치가 티 나서 역효과가 난다.

### 관통 질문
글 전체를 지탱하는 질문 하나를 앞쪽에 인용구로 심어두고, 결론에서 회수한다.
결론에서 처음 등장하는 문장보다 앞에서 심어둔 것을 되찾는 편이 글이 닫히는 느낌을 준다.

> 누가 이것을 관리하고 운용할 수 있는가?

→ (마지막 섹션) "결국 앞으로의 과제도 같은 질문으로 돌아옵니다."

**쓰지 말 것**: 글에 축이 여러 개거나 개념을 훑는 성격이면 억지 질문이 된다.

### 종단 사례
개념을 따로따로 설명한 뒤, 구체적 사례 하나로 **끝에서 끝까지 한 번 관통**시킨다.
개념들이 서로 어떻게 맞물리는지는 이 섹션에서만 보인다.

예: 병렬화 편에서 문법을 설명한 뒤 → 요청 하나가 fan-out → 수집 → 병합까지 도는 과정을 훑는다.

**쓰지 말 것**: 원문에 관통시킬 시나리오가 없으면 넣지 않는다.

## AI 사용 고지

글이나 이미지를 AI로 만들었으면 숨기지 않는다. 변명하지도 않는다.
**독자가 무엇을 기준으로 읽어야 하는지** 알려주는 형태로 인용구 한 줄을 둔다.

> 이 글의 이미지는 생성형 AI로 제작했습니다. 세부 표현에 부정확한 부분이 남아 있을 수 있으니, 이미지보다 본문의 설명을 기준으로 읽어주시기 바랍니다.

수치·날짜·링크·기여 범위는 확인한 것만 쓴다. 부풀리지 않는다.
